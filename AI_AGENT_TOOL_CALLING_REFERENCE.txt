PART 0  THE ONE IDEA YOU MUST GET RIGHT
================================================================================

The model NEVER writes a file. The model NEVER runs a command.

An LLM is a function: tokens in -> tokens out. It has no filesystem, no shell,
no network. What actually happens is:

  1. You (the harness / CLI / IDE plugin) tell the model, in the request,
     "here is a list of functions you may ask me to call, and here is the exact
      JSON shape of each one's arguments."

  2. The model, instead of (or in addition to) emitting prose, emits a
     STRUCTURED REQUEST: a block of JSON that says
         name  = "write_file"
         input = { "path": "C:\\proj\\main.py", "content": "print(1)\n" }
     and the model's turn STOPS there. It is now blocked, waiting.

  3. YOUR CODE reads that block, validates it, asks the user for permission if
     needed, and actually performs the operation with ordinary code
     (open().write(), subprocess.run(), os.remove(), ...).

  4. YOUR CODE appends the outcome back into the conversation as a
     "tool result" message, correlated by the call's id, and re-sends the WHOLE
     conversation to the model.

  5. The model sees the result and either calls another tool or writes the final
     answer to the user.

So "how does the model include in its response that you have to call this tool"
has a precise answer: it emits a dedicated content block with a reserved type
(`tool_use` on Anthropic, `tool_calls` on OpenAI, `functionCall` on Gemini) that
the provider's serializer guarantees is machine-parseable JSON, and it sets a
stop reason that tells your loop "I'm waiting on you."

Two consequences people get wrong:

  * The tool list is part of the PROMPT. It costs tokens on every single request.
    Anthropic also injects a hidden system prompt when `tools` is present (286
    tokens on Claude Opus 5.5 / Sonnet 5.5, 496 on Haiku 4.5 -- see PART 18).
  * The conversation is STATELESS. You resend the entire message array,
    including every past tool_use and tool_result, on every turn. The "agent"
    is your while-loop, not the model.

PART 1  THE AGENTIC LOOP
================================================================================

This is the whole program. Everything else in this document is detail.

    messages = [ {role: "user", content: <the user's request>} ]

    while True:
        response = provider.create_message(
            model      = "claude-opus-5-5",
            system     = SYSTEM_PROMPT,
            tools      = TOOL_SCHEMAS,          # same array every turn
            messages   = messages,
            max_tokens = 16000,
        )

        # 1. Append the assistant turn VERBATIM. Do not reformat, do not drop
        #    thinking blocks, do not keep only the text. The tool_use blocks must
        #    survive so the next request is well-formed.
        messages.append({role: "assistant", content: response.content})

        # 2. Did it ask for tools?
        if response.stop_reason != "tool_use":
            print(text_of(response))            # final answer to the user
            break

        # 3. Execute every tool_use block in this turn.
        results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            try:
                output = DISPATCH[block.name](**block.input)   # real work here
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": output,
                })
            except Exception as e:
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": f"{type(e).__name__}: {e}",
                    "is_error": True,            # tell the model it failed
                })

        # 4. ALL results go back in ONE user message, in one array.
        messages.append({role: "user", content: results})

Invariants that will bite you if you break them:

  I1. Every `tool_use` must be answered by exactly one `tool_result` with the
      matching `tool_use_id`, in the very next user message. Missing one =>
      400 from the API. Answering it two turns later => 400.
  I2. If the model emitted 3 tool_use blocks, send 3 tool_result blocks in a
      SINGLE user message. Splitting them across multiple user messages is
      accepted by some providers but teaches the model to stop issuing parallel
      calls.
  I3. A failed tool is still a result. Return is_error:true. Never silently drop
      it, and never throw the exception out of the loop -- the model usually
      recovers (fixes the path, retries with different flags) if you tell it.
  I4. Append `response.content` (the block list), not `response.text`.
  I5. Keep a hard iteration cap (e.g. 100) and a token/cost budget, or a
      confused model will loop forever on a failing command.

PART 2  WIRE FORMAT A -- ANTHROPIC MESSAGES API
================================================================================
 POST https://api.anthropic.com/v1/messages
 Headers: x-api-key: <key>
          anthropic-version: 2023-06-01
          content-type: application/json

This is the format Claude Code / Claude Agent SDK use. It is the cleanest of the
three because tool arguments arrive as a real JSON OBJECT, not a string.

--------------------------------------------------------------------------------
2.1  REQUEST -- declaring the tools
--------------------------------------------------------------------------------
{
  "model": "claude-opus-5-5",
  "max_tokens": 16000,
  "system": "You are a coding agent operating on the user's machine...",
  "tools": [
    {
      "name": "write_file",
      "description": "Write CONTENT to the file at PATH, creating parent directories as needed and overwriting any existing file. Use read_file first if the file may already exist.",
      "input_schema": {
        "type": "object",
        "properties": {
          "path":    { "type": "string",  "description": "Absolute path to the file." },
          "content": { "type": "string",  "description": "Full new contents of the file." }
        },
        "required": ["path", "content"],
        "additionalProperties": false
      },
      "strict": true
    },
    {
      "name": "run_command",
      "description": "Execute a shell command and return stdout, stderr and the exit code.",
      "input_schema": {
        "type": "object",
        "properties": {
          "command":   { "type": "string",  "description": "The command line to execute." },
          "cwd":       { "type": "string",  "description": "Working directory. Defaults to the project root." },
          "timeout_ms":{ "type": "integer", "description": "Kill the command after this many ms. Default 120000." }
        },
        "required": ["command"],
        "additionalProperties": false
      },
      "strict": true
    }
  ],
  "tool_choice": { "type": "auto" },
  "messages": [
    { "role": "user", "content": "Create hello.py that prints hi, then run it." }
  ]
}

Fields on a tool definition:
  name          [required] ^[a-zA-Z0-9_-]{1,64}$ . Must be unique.
  description   [required in practice] Plain English. See PART 8.
  input_schema  [required] A JSON Schema, draft 2020-12 subset, type "object".
  strict        [optional] true => the model's `input` is GUARANTEED to validate
                against the schema exactly. Requires "additionalProperties":
                false and a "required" list. Turn this on; it eliminates a whole
                class of KeyError at dispatch time.
  cache_control [optional] {"type":"ephemeral"} for prompt caching.
  defer_loading [optional] true => tool is hidden until the model searches for
                it with the tool-search tool. For 100+ tool setups.

tool_choice:
  {"type":"auto"}                       model decides (default)
  {"type":"auto","disable_parallel_tool_use":true}   at most one call per turn
  {"type":"none"}                       tools visible but unusable
  {"type":"any"}                        must call SOME tool
  {"type":"tool","name":"write_file"}   must call THAT tool
  NOTE: "any" and "tool" return HTTP 400 on Claude Opus 5.5, Sonnet 5.5,
  Fable 5.1 and Mythos 5.1. On those models use "auto" + an instruction in the
  prompt, plus strict:true, or use structured outputs if you only wanted JSON.

--------------------------------------------------------------------------------
2.2  RESPONSE -- the model asking for the tool
--------------------------------------------------------------------------------
HTTP 200
{
  "id": "msg_01XFDUDYJgAACzvnptvVoYEL",
  "type": "message",
  "role": "assistant",
  "model": "claude-opus-5-5",
  "content": [
    {
      "type": "text",
      "text": "I'll create the file first."
    },
    {
      "type": "tool_use",
      "id": "toolu_01A09q90qw90lq917835lq9",
      "name": "write_file",
      "input": {
        "path": "C:\\Users\\dev\\proj\\hello.py",
        "content": "print(\"hi\")\n"
      }
    }
  ],
  "stop_reason": "tool_use",
  "stop_sequence": null,
  "usage": { "input_tokens": 742, "output_tokens": 96 }
}

THIS IS THE ANSWER TO THE QUESTION "how does the model include in his response
that you have to call this tool":

  * `content` is an ARRAY of blocks, not a string.
  * A block with "type": "tool_use" IS the tool call.
  * `id` ("toolu_...") is the correlation handle. You must echo it back.
  * `name` selects which of your functions to run.
  * `input` is a decoded JSON object matching that tool's input_schema.
  * `stop_reason: "tool_use"` is the signal "I stopped early, I'm waiting."

Possible stop_reason values your loop must handle:
  "tool_use"   -> execute and continue the loop
  "end_turn"   -> model finished; print text; exit loop
  "max_tokens" -> output was truncated. A tool_use block may be INCOMPLETE.
                  Do not execute it. Retry with a bigger max_tokens.
  "pause_turn" -> long-running server tool; resend the conversation as-is
  "refusal"    -> safety decline. `stop_details.category` says why.
                  Always check this BEFORE reading content.

--------------------------------------------------------------------------------
2.3  SECOND REQUEST -- sending the result back
--------------------------------------------------------------------------------
{
  "model": "claude-opus-5-5",
  "max_tokens": 16000,
  "tools": [ ...the exact same array... ],
  "messages": [
    { "role": "user", "content": "Create hello.py that prints hi, then run it." },

    { "role": "assistant", "content": [
        { "type": "text", "text": "I'll create the file first." },
        { "type": "tool_use",
          "id": "toolu_01A09q90qw90lq917835lq9",
          "name": "write_file",
          "input": { "path": "C:\\Users\\dev\\proj\\hello.py",
                     "content": "print(\"hi\")\n" } }
    ]},

    { "role": "user", "content": [
        { "type": "tool_result",
          "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
          "content": "Wrote 12 bytes to C:\\Users\\dev\\proj\\hello.py" }
    ]}
  ]
}

tool_result block fields:
  type          "tool_result"                      [required]
  tool_use_id   must equal the tool_use's id       [required]
  content       string, OR an array of content blocks (text / image).
                Images let you return screenshots:
                  "content": [
                    {"type":"text","text":"screenshot after click"},
                    {"type":"image","source":{"type":"base64",
                       "media_type":"image/png","data":"iVBORw0..."}}
                  ]
  is_error      true if the tool failed. The text still goes in `content`.
  cache_control optional, for caching long tool outputs.

Error example:
  { "type": "tool_result",
    "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
    "content": "PermissionError: [WinError 5] Access is denied: 'C:\\\\Windows\\\\System32\\\\drivers\\\\etc\\\\hosts'",
    "is_error": true }

PART 3  WIRE FORMAT B -- OPENAI CHAT COMPLETIONS (tool_calls)
================================================================================
 POST https://api.openai.com/v1/chat/completions
 This is also the format used by every "OpenAI-compatible" endpoint: Groq,
 Together, OpenRouter, vLLM, Ollama's /v1 route, LM Studio, Azure OpenAI.
 If you are writing an agent that must work with many providers, this is the
 lowest common denominator -- which is why opencode, Cline and Continue
 normalize to it internally (usually via the Vercel AI SDK).

--------------------------------------------------------------------------------
3.1  REQUEST
--------------------------------------------------------------------------------
{
  "model": "gpt-4.1",
  "messages": [
    {"role": "system", "content": "You are a coding agent..."},
    {"role": "user",   "content": "Create hello.py that prints hi."}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "write_file",
        "description": "Write CONTENT to the file at PATH, overwriting it.",
        "parameters": {
          "type": "object",
          "properties": {
            "path":    {"type": "string"},
            "content": {"type": "string"}
          },
          "required": ["path", "content"],
          "additionalProperties": false
        },
        "strict": true
      }
    }
  ],
  "tool_choice": "auto",
  "parallel_tool_calls": true
}

Differences from Anthropic, memorize these four:
  (a) Wrapped: {"type":"function","function":{...}} instead of a flat object.
  (b) The schema key is "parameters", NOT "input_schema".
  (c) "strict": true lives INSIDE the "function" object.
  (d) tool_choice is a bare string "none"|"auto"|"required", or
      {"type":"function","function":{"name":"write_file"}}.

--------------------------------------------------------------------------------
3.2  RESPONSE
--------------------------------------------------------------------------------
{
  "id": "chatcmpl-abc123",
  "choices": [{
    "index": 0,
    "finish_reason": "tool_calls",
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [
        {
          "id": "call_9pw1q2e3r4t5y6u7i8o9",
          "type": "function",
          "function": {
            "name": "write_file",
            "arguments": "{\"path\":\"C:\\\\Users\\\\dev\\\\proj\\\\hello.py\",\"content\":\"print(\\\"hi\\\")\\n\"}"
          }
        }
      ]
    }
  }]
}

*** THE BIGGEST FOOTGUN IN TOOL CALLING ***
`function.arguments` is a STRING containing JSON, not an object. You must
json.loads() it. And because it is a string, every backslash in a Windows path
is double-escaped on the wire: the real path C:\Users became C:\\Users in the
JSON object, which became C:\\\\Users inside the JSON string literal.

  args = json.loads(tc["function"]["arguments"])   # ALWAYS do this
  path = args["path"]                              # -> C:\Users\dev\proj\hello.py

Never regex or substring-match the raw `arguments` string. Models legitimately
vary their escaping (\/ for /, \uXXXX for non-ASCII), so raw string matching
breaks at random. Without strict:true, `arguments` can also be invalid JSON, or
truncated if you hit the token limit -- wrap the parse in try/except and return
a tool error telling the model its JSON was malformed.

--------------------------------------------------------------------------------
3.3  SENDING THE RESULT BACK
--------------------------------------------------------------------------------
Append the assistant message verbatim, then ONE message per tool call with
role "tool":

  {"role": "assistant", "content": null, "tool_calls": [ ...as received... ]},
  {"role": "tool",
   "tool_call_id": "call_9pw1q2e3r4t5y6u7i8o9",
   "content": "Wrote 12 bytes to C:\\Users\\dev\\proj\\hello.py"}

Note the asymmetry with Anthropic: OpenAI uses one `tool` message PER call
(N calls -> N messages, all consecutive); Anthropic uses one `user` message
containing N blocks. There is no `is_error` flag -- signal failure in the text,
e.g. prefix with "ERROR: ".

--------------------------------------------------------------------------------
3.4  Responses API variant (newer OpenAI surface)
--------------------------------------------------------------------------------
Same concepts, flatter names. Tools are {"type":"function","name":...,
"parameters":...,"strict":true} with no nested "function" wrapper. Output items
are {"type":"function_call","call_id":"call_...","name":...,"arguments":"<json
string>"} and you reply with input items
{"type":"function_call_output","call_id":"call_...","output":"..."}.

PART 4  WIRE FORMAT C -- GOOGLE GEMINI
================================================================================
 POST https://generativelanguage.googleapis.com/v1beta/models/<model>:generateContent

REQUEST:
{
  "contents": [
    {"role": "user", "parts": [{"text": "Create hello.py that prints hi."}]}
  ],
  "tools": [{
    "functionDeclarations": [{
      "name": "write_file",
      "description": "Write CONTENT to the file at PATH, overwriting it.",
      "parameters": {
        "type": "OBJECT",
        "properties": {
          "path":    {"type": "STRING"},
          "content": {"type": "STRING"}
        },
        "required": ["path", "content"]
      }
    }]
  }],
  "toolConfig": {"functionCallingConfig": {"mode": "AUTO"}}
}

RESPONSE:
{
  "candidates": [{
    "content": {
      "role": "model",
      "parts": [{
        "functionCall": {
          "name": "write_file",
          "args": {"path": "C:\\Users\\dev\\proj\\hello.py", "content": "print(\"hi\")\n"}
        }
      }]
    },
    "finishReason": "STOP"
  }]
}

RESULT BACK (note: role is "user"/"function", there is NO id -- correlation is
by NAME and by position, which is why parallel calls to the SAME tool are
awkward on Gemini):
{
  "role": "user",
  "parts": [{
    "functionResponse": {
      "name": "write_file",
      "response": {"result": "Wrote 12 bytes to C:\\Users\\dev\\proj\\hello.py"}
    }
  }]
}

Gotchas: type names are UPPERCASE enums (STRING/OBJECT/ARRAY/INTEGER/NUMBER/
BOOLEAN); the accepted schema is a restricted OpenAPI 3 subset -- no `oneOf`,
no `$ref`, `additionalProperties` ignored; `functionResponse.response` must be
an object, so wrap plain strings in {"result": ...}.


================================================================================
PART 5  WIRE FORMAT D -- TEXT / XML PSEUDO-TOOL-CALLS
================================================================================
You need this when: the model has no native tool-calling (many local models via
llama.cpp), the provider's tool support is broken, or you deliberately want the
tool call to be visible/streamable as prose. Cline/Roo-Code historically used
this; Aider's edit formats are a variant of the same idea.

How it works: you describe the tools IN THE SYSTEM PROMPT, including a literal
syntax, and you parse the model's plain text output.

SYSTEM PROMPT EXCERPT:
    To use a tool, emit exactly one XML block and then STOP. Do not write
    anything after the closing tag. You will be given the result.

    <write_file>
    <path>absolute path here</path>
    <content>
    file contents here
    </content>
    </write_file>

    <run_command>
    <command>the command line</command>
    </run_command>

MODEL OUTPUT:
    I'll create the file.

    <write_file>
    <path>C:\Users\dev\proj\hello.py</path>
    <content>
    print("hi")
    </content>
    </write_file>

YOUR PARSER then feeds the result back as a normal user message:
    [write_file result] Wrote 12 bytes to C:\Users\dev\proj\hello.py

Why XML and not JSON for this mode: file contents contain newlines, quotes and
backslashes. In JSON those all need escaping, and models make escaping mistakes
constantly in free text. In XML-ish tags the content is literal -- no escaping,
so no corruption of Windows paths or code.

Rules if you implement this:
  * Use a stop sequence on the closing tag so the model cannot hallucinate the
    tool's result itself. This is the #1 failure of text-mode tools.
  * Accept sloppiness: trim leading/trailing newline inside <content>, accept
    missing final newline, accept attribute-free tags only.
  * Fenced-code variant used by Aider for edits:
        path/to/file.py
        <<<<<<< SEARCH
        old exact text
        =======
        new text
        >>>>>>> REPLACE
    Cheap in tokens, but fails when the SEARCH text isn't byte-exact -- which on
    Windows is usually a CRLF-vs-LF mismatch. Normalize before matching.
  * Never use text mode if native tool calling is available. You lose strict
    schema validation, you lose parallel calls, and you pay for the model
    re-deriving the syntax every turn.


================================================================================
PART 6  STREAMING: RECEIVING A TOOL CALL TOKEN BY TOKEN
================================================================================
With "stream": true you get server-sent events and must ACCUMULATE the tool
arguments from fragments. You cannot execute anything until the block closes.

--------------------------------------------------------------------------------
6.1  Anthropic SSE
--------------------------------------------------------------------------------
event: content_block_start
data: {"type":"content_block_start","index":1,
       "content_block":{"type":"tool_use","id":"toolu_01A09...","name":"write_file","input":{}}}

event: content_block_delta
data: {"type":"content_block_delta","index":1,
       "delta":{"type":"input_json_delta","partial_json":"{\"path\": \"C:\\\\Us"}}

event: content_block_delta
data: {"type":"content_block_delta","index":1,
       "delta":{"type":"input_json_delta","partial_json":"ers\\\\dev\\\\hello.py\", \"content\": \"print("}}

event: content_block_delta
data: {"type":"content_block_delta","index":1,
       "delta":{"type":"input_json_delta","partial_json":"\\\"hi\\\")\\n\"}"}}

event: content_block_stop
data: {"type":"content_block_stop","index":1}

event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"tool_use"},
       "usage":{"output_tokens":96}}

Accumulation rule: keep a dict keyed by `index`. Concatenate every
`partial_json` for that index into a buffer. On content_block_stop, json.loads()
the buffer -- that is the real `input`. The `input:{}` in content_block_start is
always an empty placeholder; never use it.

Two subtleties:
  * `partial_json` fragments split at ARBITRARY byte boundaries, including in
    the middle of a \uXXXX escape or a surrogate pair. Concatenate as strings
    and parse ONCE at the end. Do not incrementally parse.
  * By default the server buffers the tool input and emits it in a burst. Set
    `"eager_input_streaming": true` on the tool definition to have large inputs
    (file contents!) stream as generated. With it on, the API no longer
    validates or coerces the input, so the buffer may be invalid or truncated
    JSON -- guard the parse, and validate against your schema yourself before
    executing. This is what lets an editor show a file being written live.

--------------------------------------------------------------------------------
6.2  OpenAI SSE
--------------------------------------------------------------------------------
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_9pw1","type":"function",
        "function":{"name":"write_file","arguments":""}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,
        "function":{"arguments":"{\"path\":\"C:\\\\Us"}}]}}]}
data: {"choices":[{"delta":{"tool_calls":[{"index":0,
        "function":{"arguments":"ers\\\\dev\\\\hello.py\"}"}}]}}]}
data: {"choices":[{"finish_reason":"tool_calls","delta":{}}]}
data: [DONE]

Same pattern: key by `index`; `id` and `name` arrive only in the first chunk for
that index; append every `arguments` fragment; parse at finish_reason.

PART 7  THE STANDARD TOOL CATALOG OF A CODING AGENT
================================================================================
Every serious coding agent (Claude Code, opencode, Cursor, Cline, Codex CLI)
ships roughly the same 10-12 tools. The names differ; the shapes do not. Below:
the JSON Schema you put in `tools`, a realistic model-emitted call, and the
result string you should return.

Shown in Anthropic shape. To convert to OpenAI: wrap in
{"type":"function","function":{...}} and rename input_schema -> parameters.

In opencode these live in packages/opencode/src/tool/<name>.ts, each registered
with a `Tool.define(id, init)` call that returns { description, parameters,
execute }, where `parameters` is a schema and `execute(args, ctx)` does the work.
`ctx` carries sessionID, messageID, an AbortSignal, a metadata() reporter, and
an ask() function for permission prompts -- that ask() is the permission gate
described in PART 9.

7.1  read_file  (aliases: Read, view, cat)
--------------------------------------------------------------------------------
{
  "name": "read_file",
  "description": "Read a file from the filesystem and return its contents with 1-based line numbers. Prefer this over running `type` or `cat`. For files larger than 2000 lines, pass offset and limit to page through. Returns an error if the path is a directory.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path":   {"type": "string",  "description": "Absolute path to the file."},
      "offset": {"type": "integer", "description": "1-based line number to start from."},
      "limit":  {"type": "integer", "description": "Maximum number of lines to return. Default 2000."}
    },
    "required": ["path"],
    "additionalProperties": false
  },
  "strict": true
}

CALL:   {"type":"tool_use","id":"toolu_01","name":"read_file",
         "input":{"path":"C:\\proj\\src\\app.py","offset":1,"limit":50}}

RESULT: a string like
        <file path="C:\proj\src\app.py" lines="1-50 of 312">
             1  import os
             2  import sys
             3
             4  def main():
        ...
        </file>

Why line numbers: the edit tool and the model's references ("line 42") depend on
them. Why a cap: a 50k-line minified file will blow your context window and cost
you a fortune. Truncate and say so explicitly in the output -- never silently.

7.2  write_file  (aliases: Write, create, create_file)
--------------------------------------------------------------------------------
{
  "name": "write_file",
  "description": "Write CONTENT to PATH, creating parent directories as needed and OVERWRITING any existing file. If the file already exists you must read_file it first; writing blind destroys work. Prefer edit_file for changes to existing files -- use write_file only for new files or full rewrites.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path":    {"type": "string", "description": "Absolute path to the file to write."},
      "content": {"type": "string", "description": "The complete new contents of the file."}
    },
    "required": ["path", "content"],
    "additionalProperties": false
  },
  "strict": true
}

CALL:   {"type":"tool_use","id":"toolu_02","name":"write_file",
         "input":{"path":"C:\\proj\\hello.py","content":"print(\"hi\")\n"}}

RESULT: "Created C:\\proj\\hello.py (12 bytes, 1 line)."
   or   "Overwrote C:\\proj\\hello.py (312 -> 318 bytes). Diff:\n@@ -1,2 +1,3 @@\n..."

Implementation checklist (this is what opencode's write.ts actually does):
  1. Resolve the path to absolute and assert it is inside the project root
     (PART 11.10).
  2. Read the existing file if present; keep its BOM and its line-ending style.
  3. Compute a unified diff old -> new.
  4. Ask the user for permission, showing that diff (ctx.ask(...)).
  5. mkdir -p the parent, then write atomically (temp file + replace).
  6. Run the project's formatter if one is configured.
  7. Notify the LSP / file watcher, then collect new diagnostics (compile errors)
     and include them in the result -- this is how the agent notices it broke
     the build without being asked.
  8. Return relative path + byte/line counts + diagnostics.

Step 7 matters more than it looks: returning diagnostics in the tool result is
the single highest-leverage thing you can do to make an agent self-correcting.

7.3  edit_file  (aliases: Edit, str_replace, replace_in_file)
--------------------------------------------------------------------------------
{
  "name": "edit_file",
  "description": "Replace an exact substring in a file. old_string must appear EXACTLY ONCE in the file and must match byte for byte, including indentation. Include 3-5 lines of surrounding context in old_string to make it unique. Set replace_all to true to replace every occurrence. To delete code, pass an empty new_string.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path":        {"type": "string",  "description": "Absolute path to the file."},
      "old_string":  {"type": "string",  "description": "Exact text to find. Must be unique unless replace_all is true."},
      "new_string":  {"type": "string",  "description": "Text to replace it with. Must differ from old_string."},
      "replace_all": {"type": "boolean", "description": "Replace every occurrence instead of requiring uniqueness. Default false."}
    },
    "required": ["path", "old_string", "new_string"],
    "additionalProperties": false
  },
  "strict": true
}

CALL:   {"type":"tool_use","id":"toolu_03","name":"edit_file",
         "input":{"path":"C:\\proj\\hello.py",
                  "old_string":"print(\"hi\")",
                  "new_string":"import sys\nprint(\"hi\", file=sys.stderr)"}}

RESULT ok:    "Edited C:\\proj\\hello.py. 1 replacement.\n@@ -1 +1,2 @@\n-print(\"hi\")\n+import sys\n+print(\"hi\", file=sys.stderr)"
RESULT error: is_error:true,
              "old_string not found in C:\\proj\\hello.py. The file may have
               CRLF line endings while your old_string used LF, or the
               indentation differs. Re-read the file and retry."
RESULT error: is_error:true,
              "old_string appears 4 times in C:\\proj\\hello.py; it must be
               unique. Add surrounding context, or set replace_all: true."

Why this shape instead of line numbers: line numbers go stale the instant any
earlier edit lands, and models miscount. Exact-string matching fails LOUDLY
instead of corrupting the wrong line. The error messages above are part of the
tool's contract -- they are instructions the model reads and acts on. Write them
for the model, not for a human log.

Enforce "you must read_file before you edit_file" by tracking which paths this
session has read, and rejecting edits to unread files. Also record each file's
mtime at read time and reject the edit if it changed underneath you.

7.4  delete_file  (aliases: rm, remove)
--------------------------------------------------------------------------------
{
  "name": "delete_file",
  "description": "Permanently delete a file or an empty directory. This cannot be undone. Set recursive to true to delete a directory and all of its contents -- do this only when the user explicitly asked for it.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path":      {"type": "string",  "description": "Absolute path to delete."},
      "recursive": {"type": "boolean", "description": "Delete directory contents recursively. Default false."}
    },
    "required": ["path"],
    "additionalProperties": false
  },
  "strict": true
}

CALL:   {"type":"tool_use","id":"toolu_04","name":"delete_file",
         "input":{"path":"C:\\proj\\build\\temp.obj"}}

RESULT: "Deleted C:\\proj\\build\\temp.obj (4096 bytes)."

MANY AGENTS DELIBERATELY DO NOT SHIP THIS TOOL. Claude Code does not have a
delete tool; deletion goes through the shell tool so it is visible as a command
the user approves. If you do ship it:
  * ALWAYS require interactive confirmation; never allow-list it.
  * Refuse `recursive` on the project root, on any path with fewer than 2 path
    segments below the root, and on anything outside the sandbox.
  * Prefer moving to the Recycle Bin over unlink (on Windows:
    SHFileOperation / IFileOperation with FOF_ALLOWUNDO, or the `send2trash`
    package). "Cannot be undone" is a bad property for an autonomous agent.
  * On Windows expect EBUSY/EPERM when the file is open in another process --
    see PART 11.8. Report that verbatim; the model will suggest closing the
    program.

  "input_schema": {
    "type": "object",

7.7  run_command  (aliases: Bash, shell, execute_command, terminal)
--------------------------------------------------------------------------------
THE MOST POWERFUL AND MOST DANGEROUS TOOL. Read PART 11 before implementing it.

{
  "name": "run_command",
  "description": "Execute a command in the shell and return its stdout, stderr and exit code. The working directory persists between calls within a session only if persistent_session is true. Use this for builds, tests, package managers and git. Do NOT use it to read or write files -- use read_file / write_file / edit_file, which are safer and cheaper. Do not use interactive commands; they will hang until the timeout. Quote paths that contain spaces.",
  "input_schema": {
    "type": "object",
    "properties": {
      "command":     {"type":"string","description":"The command line to run."},
      "cwd":         {"type":"string","description":"Working directory. Defaults to the project root."},
      "timeout_ms":  {"type":"integer","description":"Kill the command after this many milliseconds. Default 120000, max 600000."},
      "description": {"type":"string","description":"5-10 word active-voice description of what this command does, shown to the user in the approval prompt."}
    },
    "required": ["command", "description"],
    "additionalProperties": false
  },
  "strict": true
}

CALL:   {"type":"tool_use","id":"toolu_07","name":"run_command",
         "input":{"command":"python hello.py",
                  "cwd":"C:\\proj",
                  "description":"Run the hello script"}}

RESULT (shape matters -- be explicit and machine-greppable):
  <exit_code>0</exit_code>
  <stdout>
  hi
  </stdout>
  <stderr>
  </stderr>

RESULT on failure:
  <exit_code>1</exit_code>
  <stdout>
  </stdout>
  <stderr>
  Traceback (most recent call last):
    File "C:\proj\hello.py", line 2, in <module>
      print(undefined_name)
  NameError: name 'undefined_name' is not defined
  </stderr>

RESULT on timeout (is_error: true):
  "Command timed out after 120000 ms and the process tree was killed.
   Partial stdout (last 200 lines):
   ..."

Why a `description` parameter: the user sees it in the approval prompt instead of
a wall of shell. Make the model generate it; do not generate it yourself.

Why you tell the model "do not use this to read/write files": a shell call costs
an extra process spawn, is unreviewable, bypasses your diff/permission/LSP
pipeline, and on Windows the quoting will eventually corrupt a file. Agents that
omit this line end up with models that `echo ... > file.py` and mangle it.

7.8  apply_patch  (multi-file atomic edit)
--------------------------------------------------------------------------------
Used by Codex CLI and as an alternative to many edit_file calls. One call, many
files, applied all-or-nothing.

{
  "name": "apply_patch",
  "description": "Apply a patch that may create, modify and delete multiple files atomically. If any hunk fails, nothing is changed.",
  "input_schema": {
    "type": "object",
    "properties": {"patch": {"type":"string","description":"The patch text, in the format below."}},
    "required": ["patch"], "additionalProperties": false
  }, "strict": true
}

PATCH FORMAT (a deliberately forgiving, line-number-free dialect):
  *** Begin Patch
  *** Update File: src/app.py
  @@ def main():
  -    print("hi")
  +    print("hello")
  *** Add File: src/util.py
  +def helper():
  +    return 42
  *** Delete File: src/old.py
  *** End Patch

Implementation: parse into per-file operations; for each Update, locate the
context by exact match then by whitespace-insensitive match; apply all in memory;
only then write to disk. Report per-file success. Normalize CRLF before matching
and restore each file's original ending on write (PART 11.5).

--------------------------------------------------------------------------------
7.12  ANTHROPIC-DEFINED CLIENT TOOLS (schema-less, model is pre-trained on them)
--------------------------------------------------------------------------------
For bash and file editing you can skip writing a schema entirely. Declare the
tool by TYPE and Anthropic supplies the schema the model was trained on. You
still execute it yourself and return a tool_result.

  "tools": [
    {"type": "bash_20250124", "name": "bash"},
    {"type": "text_editor_20250728", "name": "str_replace_based_edit_tool"},
    {"type": "memory_20250818", "name": "memory"}
  ]

NOTE: no "input_schema" key -- adding one, or naming your own custom tool
"bash", creates a DIFFERENT tool that the model has no training on.

The text editor tool's `input` carries a `command` discriminator:
  {"command":"view","path":"C:\\proj\\a.py","view_range":[1,50]}
  {"command":"str_replace","path":"...","old_str":"...","new_str":"..."}
  {"command":"create","path":"...","file_text":"..."}
  {"command":"insert","path":"...","insert_line":42,"insert_text":"..."}
You implement one handler per command. The bash tool's input is simply
{"command":"python hello.py"} with an optional {"restart":true} to reset the
persistent session.

Trade-off: fewer tokens and better-trained behavior, but the semantics are fixed
(e.g. the bash tool's prompt assumes a POSIX shell, which is a real friction on
Windows -- see PART 11.1). Custom tools win when you need Windows-specific
descriptions, permission metadata, or a `description` field for approval UIs.


================================================================================
PART 8  WRITING GOOD TOOL DESCRIPTIONS
================================================================================
The description is the prompt. It is the single biggest lever on agent quality --
bigger than the system prompt, bigger than the model choice at the margin.
Budget 3-6 sentences per tool, not 5 words.

Each description should answer, in this order:
  1. WHAT it does, in one sentence, in the imperative.
  2. WHEN to use it, and WHEN NOT TO -- name the competing tool.
     "Prefer this over running `type`." / "Use edit_file for existing files."
  3. The non-obvious CONSTRAINTS. "old_string must be unique." "Patterns use
     forward slashes even on Windows." "Not recursive."
  4. What it RETURNS, if that is not obvious.
  5. Failure modes and what to do about them.

Measurably effective, in rough order of payoff:
  * Name the alternative. Models over-reach for the shell because the shell can
    do everything. "Do NOT use run_command to read files" is worth more than any
    amount of system-prompt scolding.
  * Put the constraint in the PARAMETER description, not just the tool
    description. "path: ABSOLUTE path. Relative paths are rejected." The model
    reads parameter descriptions while filling in the parameter.
  * Use enums instead of prose for closed sets. `"enum":["content","count"]`
    eliminates a whole class of retry.
  * Set `strict: true` plus `additionalProperties: false`. You get schema-valid
    arguments guaranteed, which lets you drop defensive code at dispatch.
  * Make the ERROR MESSAGES part of the design. The error string is read by the
    model on the next turn; it is a second chance to teach. Compare:
        bad : "ENOENT"
        good: "File not found: C:\\proj\\src\\app.py. The directory
               C:\\proj\\src exists and contains App.py (note the capital A);
               Windows paths are case-insensitive but this tool is not."
  * Keep the tool array BYTE-STABLE across turns if you use prompt caching. Tools
    are serialized FIRST in the cache prefix, so re-ordering them or injecting a
    timestamp into a description invalidates the cache for the entire request.

Anti-patterns:
  * Dumping `--help` output into the description. Burns tokens, teaches nothing.
  * 40 tools all visible. Past ~20 the model starts picking wrong. Group them, or
    use Anthropic's tool-search with `defer_loading: true` on the long tail.
  * Overlapping tools with no stated precedence (a `read_file` and a `view_file`
    and a `cat` -- the model will pick at random and you will never know why).
  * Optional parameters with no stated default. Say "Default 2000."


================================================================================
PART 9  EXECUTING THE CALL: DISPATCH, VALIDATION, PERMISSIONS, SANDBOX
================================================================================
Order of operations for every single tool call. Do not reorder; each step exists
because skipping it caused a real incident somewhere.

  STEP 1  LOOK UP THE NAME in your registry. An unknown name is not a crash:
          return is_error with "Unknown tool 'wrtie_file'. Available tools:
          read_file, write_file, ...". The model fixes typos reliably.

  STEP 2  VALIDATE THE ARGUMENTS against the schema (jsonschema, zod, pydantic).
          Even with strict:true, validate -- strict is not available on every
          model or provider, and eager input streaming disables server-side
          validation entirely. Return the validator's error text as is_error;
          it is already a good instruction.

  STEP 3  NORMALIZE THE PATHS. Expand ~ and %VAR%, resolve relative against the
          project root (never against process.cwd(), which drifts), realpath to
          collapse symlinks/junctions, and normalize case on Windows.

  STEP 4  ENFORCE THE SANDBOX. Assert the normalized path is inside an allowed
          root. See PART 11.10 -- naive startswith() checks are bypassable.

  STEP 5  CHECK THE PERMISSION POLICY. Three outcomes:
            allow  -- run it (read-only tools, allow-listed commands)
            ask    -- prompt the user, showing the diff or the command line
            deny   -- return is_error "Denied by policy: ..." and let the model
                      choose another approach. NEVER crash the loop on a denial;
                      a denial is information for the model.
          A sane default policy:
            read_file, list_dir, glob, grep        -> allow
            write_file, edit_file, apply_patch     -> ask (show the diff)
            run_command                            -> ask, with an allow-list for
                                                      known-safe read-only
                                                      commands (git status,
                                                      git diff, ls, dir)
            delete_file                            -> always ask, never allow-list
          Remember the user's answer per (tool, pattern) for the session only --
          persisting "always allow run_command" across sessions is how an agent
          eventually runs something destructive unattended.

  STEP 6  EXECUTE, with: a timeout, an AbortSignal/CancellationToken wired to the
          user pressing Esc, and a byte cap on captured output.

  STEP 7  TRUNCATE AND FORMAT the result (PART 10).

  STEP 8  AUDIT LOG the call: timestamp, tool, arguments, decision, exit status,
          duration. You will need this the first time an agent does something
          surprising.

Sandboxing beyond path checks -- pick a level and be honest about it:
  Level 0  Nothing. The agent can do anything the user can. (Most CLI agents in
           their default mode. Fine if a human approves each command.)
  Level 1  Path containment + command allow-list + no network for tools.
  Level 2  OS-level: a restricted user token / Job Object / AppContainer on
           Windows; seccomp+namespaces or bubblewrap on Linux; sandbox-exec on
           macOS. Filesystem mounted read-only except the project directory.
  Level 3  A disposable container or VM with the repo mounted. The only level
           that is actually safe against a malicious instruction smuggled in via
           a file the agent reads, a web page it fetches, or a dependency's
           postinstall script. Prompt injection is the real threat model for a
           coding agent, not the model deciding to be evil.

Treat as UNTRUSTED DATA, never as instructions: file contents, command output,
web pages, issue/PR text, dependency manifests, and MCP tool results. If content
read by a tool tries to redirect the task or escalate access, surface it to the
user rather than acting on it.


================================================================================
PART 10  RETURNING RESULTS: SUCCESS, ERROR, TRUNCATION, METADATA
================================================================================
A tool result is a prompt fragment. Design it like one.

RULES
  R1. Always return SOMETHING. An empty result makes the model re-call the tool.
      For a command with no output, return "<exit_code>0</exit_code> (no output)".
  R2. Put the most important fact first. Exit code before stdout. "ERROR:" first.
  R3. Delimit multi-part output with tags, not blank lines. <stdout>...</stdout>
      survives the model's attention better than whitespace, and lets you include
      content that itself contains blank lines.
  R4. Echo back what you actually did, not what was asked. "Wrote 318 bytes to
      C:\proj\a.py" -- resolved absolute path, real byte count. The model builds
      its world model from these strings.
  R5. Include derived signals the model would otherwise have to go get:
      diagnostics after an edit, the diff, the new line count, the test summary
      line. Every signal you include is a tool call you do not pay for later.
  R6. TRUNCATE, and say so, in a way that tells the model how to get the rest:
          [output truncated: 12,842 of 48,110 lines shown. Re-run with
           `... | Select-Object -Last 200` or grep for the failing test name.]
      Truncate from the MIDDLE for build logs (the first lines have the command,
      the last lines have the error; the middle is noise). Cap at ~30k characters
      or ~8k tokens per result.
  R7. Strip ANSI escape sequences and carriage-return progress bars before
      returning. An npm install progress bar can be 200KB of \r junk that teaches
      the model nothing and costs real money.
  R8. On error, return the EXACT error text plus a hint. Do not sanitize OS error
      messages -- "[WinError 32] The process cannot access the file because it is
      being used by another process" is immediately actionable for the model;
      "write failed" is not.
  R9. Never fabricate a result. If you could not run it, say so with is_error.
      A fabricated success is the worst possible outcome: the model proceeds on a
      false premise for the rest of the session.
  R10. Secrets: redact tokens/keys from command output before they enter the
      transcript. The transcript gets resent to the provider on every turn.


================================================================================
PART 11  WINDOWS: EVERYTHING THAT IS DIFFERENT
================================================================================
The wire format is identical on every OS. The EXECUTION side is where Windows
diverges, and every item below is a bug people actually ship.

--------------------------------------------------------------------------------
11.1  WHICH SHELL TO SPAWN
--------------------------------------------------------------------------------
There is no /bin/sh. You have four realistic choices:

 (a) cmd.exe  -- always present, worst language.
       cmd.exe /d /s /c "<command line>"
         /d  skip AutoRun registry commands (HKCU\...\Command Processor\AutoRun).
             ALWAYS pass /d: without it, a user's AutoRun runs before every
             single command you execute.
         /s  take the rest of the line literally after stripping the outer quotes
             (makes quoting predictable -- see 11.2).
         /c  run and terminate.

 (b) PowerShell -- good language, slow start (~250ms+), profile side effects.
       powershell.exe -NoProfile -NonInteractive -NoLogo \
                      -ExecutionPolicy Bypass -Command "<command>"
       pwsh.exe        (PowerShell 7+, cross-platform, prefer if installed)
         -NoProfile       skip the user's $PROFILE (which may print banners that
                          corrupt your stdout parsing, or change the encoding)
         -NonInteractive  make prompts fail instead of hanging forever
       Detect pwsh first:  where.exe pwsh.exe   then fall back to powershell.exe.

 (c) Git Bash / MSYS2 -- POSIX-ish, present on most dev machines, path mangling.
       "C:\Program Files\Git\bin\bash.exe" -lc "<command>"
       Set MSYS_NO_PATHCONV=1 (and/or MSYS2_ARG_CONV_EXCL=*) or MSYS will
       "helpfully" rewrite an argument like /c into C:/Program Files/...

 (d) WSL -- a different machine with a different filesystem.
       wsl.exe -e bash -lc "<command>"
       /mnt/c/... paths, LF endings, separate toolchain. Do not silently mix WSL
       and Win32 tools in one session: a venv created in WSL will not run under
       Win32 Python, and file watchers across /mnt/c are slow and lossy.

RECOMMENDATION for an agent: pick ONE per session, detect it at startup, and
PUT THE ANSWER IN THE SYSTEM PROMPT. This single line removes most Windows
failures:

    "You are on Windows 11. The run_command tool executes commands with
     PowerShell 7 (pwsh). Use PowerShell syntax: `Get-ChildItem` not `ls`,
     `$env:VAR` not `$VAR`, `;` to chain, `-not` not `!`. Paths use backslashes.
     `python` resolves to C:\Python313\python.exe."

Without it the model defaults to POSIX habits (ls, grep, rm -rf, &&, $HOME,
2>/dev/null, which) and burns 3-4 turns rediscovering the OS. Note that
`cmd.exe` does support `&&` and `||`; PowerShell 5.1 does NOT (they arrived in
PowerShell 7). `ls` and `cat` exist in PowerShell as aliases but take different
flags -- `ls -la` fails.

Persistent vs per-call shells:
  Per-call (spawn a fresh shell each time) is simpler and stateless, but `cd`,
  `activate`, and `set VAR=` do not persist. Tell the model that.
  Persistent (keep one shell alive, write commands to its stdin, delimit output
  with a random sentinel you echo after each command) preserves state but you
  must handle: the shell dying, a command that reads stdin and eats your next
  command, and recovering the exit code (`echo __DONE__$LASTEXITCODE` on
  PowerShell, `echo __DONE__%ERRORLEVEL%` on cmd). Anthropic's `bash_20250124`
  tool assumes persistent-session semantics and exposes {"restart":true}.

11.2  QUOTING AND ARGUMENT ESCAPING
--------------------------------------------------------------------------------
Windows has no argv. CreateProcess takes ONE STRING, and each program parses it
itself. The usual parser is CommandLineToArgvW, whose rules are:
    "  starts/ends a quoted region (and is removed)
    \" is a literal quote
    \\ before a quote is one literal backslash
    backslashes NOT followed by a quote are literal
So:  C:\proj\  as a quoted argument must be written  "C:\proj\\"  -- because
     "C:\proj\"  ends with an escaped quote and swallows the closing quote.
     This is the classic "trailing backslash on a directory path" bug.

cmd.exe does NOT use those rules. It pre-processes the line for
    % ! ^ & | < > ( ) ,  ; = space
Escape with ^ (and %% for a literal % in a batch file). %VAR% is expanded even
inside double quotes. !VAR! is expanded if delayed expansion is on.

PowerShell adds a THIRD layer: it parses the string, then re-builds a command
line for the native process. $ ` and " are special; single quotes are literal.
PowerShell 7.3+ fixed most native-argument passing; 5.1 did not --
`--define="a b"` silently loses the quotes on 5.1.

PRACTICAL RULES
  * NEVER build a command line by concatenating strings with user/model data.
  * For run_command, you are handed a command LINE by the model -- pass it
    through to the shell verbatim and let the shell parse it. Do not try to
    "fix" the quoting; you will break more than you repair.
  * For every other tool (write_file, read_file, delete_file) DO NOT GO THROUGH
    A SHELL AT ALL. Call the filesystem API directly. This is the single most
    important Windows rule in this document: it eliminates quoting, escaping,
    encoding and metacharacter problems in one move.
  * When you must spawn a program with arguments, pass an ARGUMENT ARRAY and let
    your runtime do the escaping:
        Python : subprocess.run([exe, "--path", p])      shell=False
        Node   : spawn(exe, ["--path", p])               no shell: true
        .NET   : ProcessStartInfo.ArgumentList.Add(p)    never .Arguments
  * To escape PowerShell quoting entirely for a generated script, use
    -EncodedCommand with base64 of UTF-16LE:
        $b = [Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes($cmd))
        pwsh -NoProfile -EncodedCommand $b
    In Python:  base64.b64encode(cmd.encode("utf-16-le")).decode()
    This is the bulletproof way to run a multi-line generated script.
  * Or: write the script to a temp .ps1/.cmd file and execute the FILE. One
    argument, no escaping. Delete it in a finally block.

11.3  ENCODING / CODE PAGES / MOJIBAKE
--------------------------------------------------------------------------------
Symptom: the model sees "Ð¿Ñ€Ð¸Ð²ÐµÑ‚" or "â" or "ΓêÆ" in tool output and starts
"fixing" encoding bugs that do not exist.

Cause: a console program writes bytes in the ACTIVE CODE PAGE (cp437 or cp850 in
a legacy console, cp1252-ish elsewhere), and you decode them as UTF-8 (or vice
versa).

Fixes, apply all of them:
  * Set the code page for the child: prefix the command with `chcp 65001>nul & `
    for cmd, or run `[Console]::OutputEncoding=[Text.Encoding]::UTF8` in
    PowerShell before the command.
  * Set environment variables for the child process:
        PYTHONIOENCODING=utf-8
        PYTHONUTF8=1
        DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=0
  * Capture BYTES, not text, and decode explicitly with errors="replace" so one
    bad byte never throws:
        out = proc.stdout.decode("utf-8", errors="replace")
    If you know the console code page, try it first:
        import ctypes; cp = ctypes.windll.kernel32.GetConsoleOutputCP()
        out = raw.decode(f"cp{cp}", errors="replace")
  * In Node: child_process gives you Buffers by default -- do NOT set
    encoding:'utf8' blindly; decode with iconv-lite using the real code page if
    the output looks wrong.
  * Enable the Windows 10+ per-process UTF-8 manifest for your own agent binary
    if you ship one.
  * Strip ANSI/VT sequences after decoding, not before (they are ASCII, so order
    rarely matters, but a half-decoded buffer can split an escape sequence).

Also: UTF-8 BOM. Many Windows tools (PowerShell 5.1's Set-Content, Visual
Studio, Notepad) write EF BB BF at the start of files. If your read_file strips
it and write_file does not restore it, you silently change the file and some
compilers (and `git diff`) will notice. opencode's write tool explicitly
preserves the BOM. Do the same: detect on read, re-emit on write.

11.4  PATHS: SEPARATORS, JSON ESCAPING, LONG PATHS, RESERVED NAMES
--------------------------------------------------------------------------------
JSON ESCAPING -- the #1 source of "the model sent a broken path":
    real path                 C:\Users\dev\proj\a.py
    inside a JSON object      "C:\\Users\\dev\\proj\\a.py"
    inside an OpenAI
    `arguments` JSON STRING   "{\"path\":\"C:\\\\Users\\\\dev\\\\proj\\\\a.py\"}"
  Four backslashes in the raw bytes is CORRECT in that last case. Always
  json.loads() and never count backslashes by eye.
  Models sometimes emit a single backslash ("C:\Users") which is INVALID JSON
  ( \U is an illegal escape). With strict:true the provider rejects it for you;
  without it, your parse fails -- return is_error telling the model to use
  forward slashes or double backslashes, and consider accepting forward slashes
  everywhere to sidestep the whole problem.

SEPARATORS
  * The Win32 API accepts forward slashes almost everywhere, so
    open("C:/proj/a.py") works. Your tools should ACCEPT both and NORMALIZE.
  * cmd.exe built-ins and many CLI tools do NOT accept forward slashes, because
    `/` starts a switch (`dir /s`). So never feed a forward-slash path into a
    cmd.exe command line.
  * Glob patterns should use forward slashes (that is what every glob library
    expects). Say so in the tool description.
  * Return paths to the model in the platform's native form (backslashes) so the
    model can paste them into commands. Be consistent -- mixing styles in your
    output makes the model mix them in its calls.

OTHER PATH FACTS
  * MAX_PATH = 260 characters, unless the process opts in (manifest
    longPathAware + the LongPathsEnabled registry key) or the path is prefixed
    \\?\ (which also disables all normalization -- no . or .. or / allowed).
    `npm install` in a deep monorepo on Windows fails for exactly this reason.
  * UNC paths: \\server\share\... and \\?\UNC\server\share\...
  * Case-insensitive but case-PRESERVING (unless per-directory case sensitivity
    is enabled). "App.py" and "app.py" are the same file; your "have I read this
    file" bookkeeping must normalize case, or the model will edit a file it
    "never read".
  * Reserved device names, in ANY directory, with ANY extension:
      CON PRN AUX NUL COM1-COM9 LPT1-LPT9  (also COM¹ COM² COM³ variants)
    Writing to "nul.txt" silently writes to the null device. Reject these.
  * Illegal characters in a filename:  < > : " | ? *  and chars 0-31.
    Note ':' -- a path like "C:\a\b:c.txt" creates an NTFS ALTERNATE DATA STREAM,
    not a file. Reject ':' except as the drive separator at index 1.
  * Trailing dots and spaces are silently STRIPPED by Win32. "a.py " and "a.py."
    both resolve to "a.py". Normalize before comparing.
  * 8.3 short names ("PROGRA~1") resolve to the same file as the long name. A
    sandbox check must expand them (GetLongPathNameW).
  * Drive-relative paths are a thing: "C:foo" means "foo relative to the current
    directory ON DRIVE C", which is NOT "C:\foo". Reject or resolve explicitly.

11.5  CRLF LINE ENDINGS
--------------------------------------------------------------------------------
This breaks edit_file more than anything else on Windows.

The model emits old_string with "\n". The file on disk has "\r\n". Exact match
fails. The model retries with the same string, fails again, and eventually
rewrites the whole file with write_file -- losing the original endings and
producing a diff that touches every line.

FIX (do all four):
  1. Read files in BINARY and decode yourself. Never open in text mode with
     universal newlines for an edit tool -- you lose the information you need.
  2. DETECT the dominant ending per file and remember it:
        crlf = content.count("\r\n");  lf = content.count("\n") - crlf
        eol  = "\r\n" if crlf >= lf else "\n"
  3. MATCH with both sides normalized to "\n". Normalize the file content and
     the model's old_string, find the match in normalized space, map the offsets
     back, and splice in the original bytes.
     Simplest correct approach: normalize the file to LF, apply the edit, then
     convert the whole result back to the detected `eol` on write.
  4. WRITE with the detected ending, and preserve the BOM and the
     presence/absence of a trailing newline.
  Also respect .gitattributes / core.autocrlf if the repo declares them, and tell
  the model in the tool description that endings are handled automatically so it
  does not try to "fix" them.

11.6  .cmd / .bat / PATHEXT RESOLUTION (AND THE SECURITY HOLE)
--------------------------------------------------------------------------------
On Windows, `npm`, `yarn`, `tsc`, `eslint`, `pip`, `az` are NOT executables.
They are npm.cmd / tsc.cmd / pip.exe shims. CreateProcess can only start .exe
and .com; it cannot execute a .cmd. Consequences:

  * subprocess.run(["npm","install"]) with shell=False raises
    FileNotFoundError/WinError 2, even though `npm install` works in a terminal.
    The terminal worked because cmd.exe consulted %PATHEXT%
    (.COM;.EXE;.BAT;.CMD;.VBS;...) to find npm.cmd.
  * Fixes, in order of preference:
      (i)  resolve the real file yourself with shutil.which("npm") (Python
           honors PATHEXT) and spawn that exact path;
      (ii) spawn via the shell explicitly (cmd.exe /d /s /c "npm install");
      (iii) shell=True / shell:true  -- acceptable for the run_command tool,
            where the model hands you a whole command line anyway.
  * SECURITY: because cmd.exe re-parses the command line for a .bat/.cmd, an
    argument containing & | ^ " can inject a second command. This was
    CVE-2024-27980 in Node.js; modern Node REFUSES to spawn .bat/.cmd without
    shell:true so that the escaping decision is explicit, and Python's
    subprocess has the same exposure via list2cmdline. So: never interpolate
    untrusted data (including model output, including file contents) into an
    argument of a batch file. Validate against an allow-list or write the value
    to a temp file and pass the file path.

Also worth knowing:
  * Environment variable names are CASE-INSENSITIVE on Windows ("Path" ==
    "PATH"). If you build the child's env dict yourself, de-duplicate
    case-insensitively or you can end up with an empty effective PATH.
  * `where.exe <cmd>` is the Windows `which`. PowerShell has Get-Command.
  * A command not found gives exit code 9009 from cmd.exe (and 1 plus a
    CommandNotFoundException from PowerShell). Translate 9009 in your result
    text: "exit 9009 -- command not found on PATH".

11.7  TIMEOUTS AND KILLING PROCESS TREES
--------------------------------------------------------------------------------
There are no POSIX process groups and no SIGTERM. Problems this causes:

  * You spawn cmd.exe, which spawns node, which spawns a watcher. You kill
    cmd.exe. node and the watcher KEEP RUNNING, still holding your stdout pipe
    open, so your read never returns and your "timeout" never completes. The
    agent appears to hang forever on `npm run dev`.

  * proc.kill() / TerminateProcess is a hard kill. The child gets no chance to
    flush buffers or clean up temp files. There is no graceful signal (a console
    Ctrl+C event can be sent with GenerateConsoleCtrlEvent, but only to
    processes sharing your console, which a hidden child does not).

DO THIS:
  * Kill the TREE, not the process:
        taskkill /PID <pid> /T /F
    /T = tree, /F = force. From code:
        Python: subprocess.run(["taskkill","/PID",str(p.pid),"/T","/F"],
                               capture_output=True)
        Node  : spawn("taskkill",["/pid",String(child.pid),"/t","/f"])
                or use the `tree-kill` package
  * Better: create the child in a JOB OBJECT with
    JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE. Closing the job handle kills every
    descendant, atomically, with no race against a process that forks after your
    taskkill enumerates. This is what robust agents do. In Node:
    spawn with { detached: false, windowsHide: true } plus a native job-object
    addon; in .NET, use the Win32 CreateJobObject/AssignProcessToJobObject APIs.
  * Always pass windowsHide: true (Node) / CREATE_NO_WINDOW (Win32) or every
    command flashes a console window on the user's screen.
  * Close/drain the stdout and stderr pipes after the kill, with their own short
    timeout, or you will still block.
  * Set a DEFAULT timeout (120s is a good default, 600s a good max) and tell the
    model the number in the tool description, so it knows to background long
    jobs rather than burn a turn on a timeout.
  * For deliberately long-running jobs (dev servers, watchers), do not use the
    normal path at all: start them detached, redirect output to a log file, and
    give the model a separate tool to tail that log. A dev server in a
    foreground tool call is a guaranteed timeout.

11.8  FILE LOCKING: WHY DELETE AND RENAME FAIL
--------------------------------------------------------------------------------
POSIX lets you unlink an open file. Windows does not (unless it was opened with
FILE_SHARE_DELETE, which almost nothing does). So:

  * delete_file on a file open in an editor, a running process's loaded DLL, or
    a file being scanned by Windows Defender / a search indexer fails with
    [WinError 32] "The process cannot access the file because it is being used
    by another process", surfaced as PermissionError / EBUSY / EPERM.
  * Removing a directory fails if ANY file under it is open, or if any process's
    current directory is inside it -- including a shell your own agent left
    running.
  * Atomic write via temp-file-plus-rename can fail for the same reason: on
    Windows os.replace()/MoveFileEx over an OPEN target raises. Use
    ReplaceFileW (which handles more cases and preserves ACLs/attributes), or
    retry with backoff, or fall back to truncate-and-write-in-place.

PRACTICAL HANDLING
  * Retry transient failures 3-5 times with 50-200ms backoff. Antivirus locks
    are usually gone within a few hundred milliseconds. This one trick removes
    most flaky-write reports on Windows.
  * On final failure, return the OS error VERBATIM plus a hint: "...is being
    used by another process. If you have the file open in an editor or a dev
    server is running, close it and retry." The model relays this to the user,
    which is exactly right -- you cannot fix it from code.
  * Prefer moving to the Recycle Bin over unlink for delete_file.
  * Never hold your own read handle open while you write. Read fully, close,
    then write.

11.9  EXIT CODES YOU WILL ACTUALLY SEE
--------------------------------------------------------------------------------
  0            success
  1            generic failure (also PowerShell's command-not-found)
  2            often "file not found" / bad usage from Unix-style tools
  9009         cmd.exe: command not found on PATH            <-- translate this
  3221225477   0xC0000005  ACCESS_VIOLATION (the process crashed)
  3221225786   0xC000013A  terminated by Ctrl+C / Ctrl+Break
  3221225781   0xC0000135  a required DLL was not found (missing VC++ runtime)
  -1073741819  the same as 3221225477, as a signed 32-bit int. Your runtime may
               report either. Normalize with (code & 0xFFFFFFFF) before
               comparing, and print the hex form in the result.
  5            Access denied, from some tools
  Large/negative values are usually NTSTATUS codes -- include the hex in the
  result text so the model can recognize them.

PowerShell specifics:
  * $LASTEXITCODE holds a native program's exit code; $? holds a boolean.
  * A PowerShell CMDLET that errors does NOT by default set a nonzero process
    exit code. `pwsh -Command "Get-Item missing"` exits 0 (PS 5.1) unless you
    end with `exit $LASTEXITCODE` or set $ErrorActionPreference='Stop' and use
    a trap. If your run_command returns exit 0 for a visibly failed command, the
    model will believe it succeeded. So: append `; exit $LASTEXITCODE` to
    PowerShell command lines, and set $ErrorActionPreference = 'Stop' in the
    preamble.

11.10  PATH-CONTAINMENT (SANDBOX) CHECK DONE CORRECTLY
--------------------------------------------------------------------------------
The naive check is bypassable in at least six ways on Windows.

  WRONG:   if path.startswith(root): allow()
  Bypasses: "C:\proj2" startswith "C:\proj"          (prefix, not ancestor)
            "C:\proj\..\..\Windows\System32\..."     (traversal)
            "C:\PROJ\secrets.env"                    (case)
            "C:\PROGRA~1\..."                        (8.3 short name)
            a junction/symlink inside the project pointing at C:\
            "\\?\C:\proj\..\Windows"                 (prefix disables
                                                      normalization)
            "C:a.py"                                 (drive-relative)

  CORRECT (Python):
      import os
      def contained(root: str, candidate: str) -> str:
          # 1. reject drive-relative and device paths up front
          if candidate.startswith("\\\\?\\") or candidate.startswith("\\\\.\\"):
              raise ValueError("device/extended paths are not allowed")
          # 2. make absolute against the ROOT, never against process cwd
          p = candidate if os.path.isabs(candidate) else os.path.join(root, candidate)
          # 3. resolve .. and symlinks/junctions and 8.3 names
          p    = os.path.realpath(p)
          root = os.path.realpath(root)
          # 4. ancestor test on normalized, case-folded components
          try:
              rel = os.path.relpath(p, root)
          except ValueError:          # different drive letters
              raise PermissionError(f"outside project root: {p}")
          if rel == ".." or rel.startswith(".." + os.sep) or os.path.isabs(rel):
              raise PermissionError(f"outside project root: {p}")
          # 5. reject reserved device names on every component
          RESERVED = {"con","prn","aux","nul",*(f"com{i}" for i in range(1,10)),
                               *(f"lpt{i}" for i in range(1,10))}
          for part in rel.split(os.sep):
              if part.split(".")[0].lower() in RESERVED:
                  raise PermissionError(f"reserved device name: {part}")
          return p

  Notes:
   * os.path.realpath on Windows resolves symlinks, junctions AND expands 8.3
     short names on modern Python. On older runtimes call GetLongPathNameW.
   * Do the realpath BEFORE the comparison, and realpath the ROOT too -- if the
     project lives under a junction, a non-resolved root never matches a
     resolved candidate and every call is denied.
   * There is an inherent TOCTOU race: a junction can be created between your
     check and your open(). For high-assurance setups, open the file with
     FILE_FLAG_OPEN_REPARSE_POINT semantics or do the work inside a container
     (PART 9, level 3).
   * Apply the same check to the `cwd` of run_command, and to every path inside
     a patch.

PART 12  PARALLEL TOOL CALLS AND MESSAGE ORDERING RULES
================================================================================
A single assistant turn may contain SEVERAL tool_use blocks. This is on by
default on Anthropic and OpenAI.

    "content": [
      {"type":"text","text":"Let me look at all three files."},
      {"type":"tool_use","id":"toolu_A","name":"read_file","input":{"path":"C:\\p\\a.py"}},
      {"type":"tool_use","id":"toolu_B","name":"read_file","input":{"path":"C:\\p\\b.py"}},
      {"type":"tool_use","id":"toolu_C","name":"grep","input":{"pattern":"main"}}
    ]

Your loop must:
  * Execute them -- concurrently if they are independent, which for reads they
    are. Three sequential 80ms reads is 240ms; three concurrent is 80ms, and the
    model issued them together precisely so you would overlap them.
  * Return ALL results in ONE user message, as one array of tool_result blocks.
    Order within the array does not matter (correlation is by id), but all must
    be present.
  * Still return a result for the ones that failed, with is_error.

Do NOT parallelize blindly. Serialize when calls touch the same file, or when one
is a write and another is a read of the same path. The model does occasionally
emit `edit_file(a.py)` twice in one turn with overlapping old_strings; apply them
in array order, and if the second fails because the first changed the text,
return that error -- the model will re-read and retry.

To disable parallelism: tool_choice {"type":"auto","disable_parallel_tool_use":
true} (Anthropic) or "parallel_tool_calls": false (OpenAI). Worth doing for
destructive tools, or while debugging your loop.

ORDERING RULES THAT CAUSE HTTP 400 IF BROKEN (Anthropic):
  * A user message containing tool_result blocks must IMMEDIATELY follow the
    assistant message containing the tool_use blocks. You may not insert a
    plain user message in between. If the user types something while tools are
    running, queue it and send it in the NEXT user turn, after the results (or
    append it as an extra text block in the same user message, after the
    tool_result blocks).
  * Every tool_use needs a matching tool_result; every tool_result needs a
    matching tool_use. No orphans in either direction.
  * tool_result blocks must come FIRST in the user message's content array; text
    blocks after them.
  * Preserve thinking blocks verbatim in the assistant turn when thinking is on.
    On current Claude models, editing earlier turns invalidates thinking blocks
    ("preserved thinking") -- so keep your history APPEND-ONLY. Do not rewrite,
    re-order or drop earlier messages mid-conversation; if you need to shrink
    history, use the API's own context-editing/compaction features rather than
    mutating the array yourself.

PART 13  MCP: LOADING TOOLS FROM EXTERNAL SERVERS
================================================================================
Model Context Protocol is how an agent acquires tools it did not ship with
(a database client, a Jira client, a browser driver) without recompiling.

Mechanically, MCP changes NOTHING about the wire format in PARTS 2-4. It is a
discovery and transport layer that sits in front of your tool registry:

  1. Your agent launches or connects to an MCP server. Transports:
       stdio -- you spawn a process and speak JSON-RPC 2.0 over its
                stdin/stdout. On Windows this means spawning `npx`/`uvx`, which
                are .cmd shims -- see PART 11.6, this is the #1 reason MCP
                servers "don't work on Windows". Resolve the real path with
                where.exe/shutil.which, or spawn through cmd.exe /d /s /c.
       HTTP  -- streamable HTTP / SSE to a URL, usually with an auth header.
  2. You send `initialize`, then `tools/list`. The server returns tool
     descriptors: {name, description, inputSchema} -- already JSON Schema.
  3. You TRANSLATE each descriptor into your provider's tool format (add the
     input_schema/parameters key, namespace the name) and append it to the
     `tools` array you send the model. Namespacing matters:
         mcp__postgres__query      (Claude Code convention)
         postgres.query
     Without a namespace, two servers that both expose `search` collide.
  4. When the model emits a tool_use for a namespaced name, you route the
     `input` to that server as a JSON-RPC `tools/call`, and wrap the server's
     response content back into a tool_result.

Operational cautions:
  * MCP tool descriptions and results are UNTRUSTED. A server's description is
    injected into your prompt; a server's result is read by the model as fact.
    A malicious or compromised server can attempt prompt injection. Treat server
    output as data (PART 9), namespace aggressively, and let the user approve
    which servers load.
  * Each server's tools cost prompt tokens on every turn. Ten servers with
    fifteen tools each will degrade tool selection and blow your cache. Use
    defer_loading / tool-search for the long tail.
  * Anthropic also offers an MCP connector that calls remote MCP servers
    server-side: declare both mcp_servers=[{type:"url",url,name}] AND
    tools=[{type:"mcp_toolset", mcp_server_name:"<same name>"}] -- passing only
    the first is a validation error.

import base64, ctypes, json, os, re, shutil, subprocess, sys, time
import anthropic

MODEL = "claude-opus-5-5"
ROOT = os.path.realpath(os.getcwd())
IS_WIN = os.name == "nt"
MAX_RESULT_CHARS = 30_000
MAX_ITERS = 60

# ---------------------------------------------------------------- path safety
RESERVED = {"con", "prn", "aux", "nul", *(f"com{i}" for i in range(1, 10)),
            *(f"lpt{i}" for i in range(1, 10))}

def safe_path(candidate: str) -> str:
    """Normalize and assert the path is inside ROOT. Raises PermissionError."""
    if not candidate or not candidate.strip():
        raise ValueError("path must not be empty")
    if candidate.startswith("\\\\?\\") or candidate.startswith("\\\\.\\"):
        raise PermissionError("extended/device paths are not allowed")
    if IS_WIN and re.match(r"^[A-Za-z]:(?![\\/])", candidate):
        raise PermissionError(f"drive-relative path is ambiguous: {candidate!r}")
    p = candidate if os.path.isabs(candidate) else os.path.join(ROOT, candidate)
    p = os.path.realpath(os.path.expanduser(os.path.expandvars(p)))
    try:
        rel = os.path.relpath(p, ROOT)
    except ValueError:
        raise PermissionError(f"outside project root (other drive): {p}")
    if rel == ".." or rel.startswith(".." + os.sep) or os.path.isabs(rel):
        raise PermissionError(f"outside project root: {p}")
    for part in rel.split(os.sep):
        stem = part.split(".")[0].lower().rstrip(" .")
        if IS_WIN and stem in RESERVED:
            raise PermissionError(f"reserved Windows device name: {part}")
    return p

# ------------------------------------------------- encoding / eol / bom helpers
BOM = b"\xef\xbb\xbf"

def read_text(path: str):
    """-> (text_with_LF, eol, had_bom)"""
    raw = open(path, "rb").read()
    had_bom = raw.startswith(BOM)
    if had_bom:
        raw = raw[len(BOM):]
    text = raw.decode("utf-8", errors="replace")
    crlf = text.count("\r\n")
    lf = text.count("\n") - crlf
    eol = "\r\n" if crlf > lf else "\n"
    return text.replace("\r\n", "\n"), eol, had_bom

def write_text(path: str, text_lf: str, eol: str = "\n", bom: bool = False):
    data = text_lf.replace("\n", eol).encode("utf-8")
    if bom:
        data = BOM + data
    os.makedirs(os.path.dirname(path) or ".", exist_ok=True)
    tmp = path + f".tmp{os.getpid():x}"
    with open(tmp, "wb") as f:
        f.write(data)
        f.flush()
        os.fsync(f.fileno())
    # Windows: os.replace can fail if the target is open. Retry past AV locks.
    for attempt in range(5):
        try:
            os.replace(tmp, path)
            return len(data)
        except PermissionError:
            if attempt == 4:
                try: os.remove(tmp)
                except OSError: pass
                raise
            time.sleep(0.05 * (2 ** attempt))

def console_cp_decode(raw: bytes) -> str:
    if IS_WIN:
        try:
            cp = ctypes.windll.kernel32.GetConsoleOutputCP() or 65001
        except Exception:
            cp = 65001
        if cp != 65001:
            try:
                return raw.decode(f"cp{cp}", errors="replace")
            except LookupError:
                pass
    return raw.decode("utf-8", errors="replace")

ANSI = re.compile(r"\x1b\[[0-9;?]*[ -/]*[@-~]|\x1b\][^\x07\x1b]*(?:\x07|\x1b\\)")

def clean_output(raw: bytes) -> str:
    text = console_cp_decode(raw)
    text = ANSI.sub("", text)
    text = re.sub(r"[^\n]*\r(?!\n)", "", text)   # collapse progress bars
    return text.replace("\r\n", "\n")

def truncate(text: str, limit: int = MAX_RESULT_CHARS) -> str:
    if len(text) <= limit:
        return text
    head, tail = text[: limit // 2], text[-limit // 2 :]
    omitted = len(text) - limit
    return (f"{head}\n\n[... {omitted} characters omitted from the middle; "
            f"{len(text)} total. Re-run filtered (e.g. pipe through "
            f"Select-String) to see more ...]\n\n{tail}")

# ------------------------------------------------------------- shell selection
def pick_shell():
    if not IS_WIN:
        return ("/bin/bash", ["-lc"], "bash")
    pwsh = shutil.which("pwsh") or shutil.which("pwsh.exe")
    if pwsh:
        return (pwsh, ["-NoProfile", "-NonInteractive", "-NoLogo",
                       "-ExecutionPolicy", "Bypass", "-Command"], "pwsh")
    ps = shutil.which("powershell") or shutil.which("powershell.exe")
    if ps:
        return (ps, ["-NoProfile", "-NonInteractive", "-NoLogo",
                     "-ExecutionPolicy", "Bypass", "-Command"], "powershell")
    return (os.environ.get("COMSPEC", "cmd.exe"), ["/d", "/s", "/c"], "cmd")

SHELL_EXE, SHELL_ARGS, SHELL_KIND = pick_shell()

def wrap_command(cmd: str) -> str:
    if SHELL_KIND in ("pwsh", "powershell"):
        return ("$ErrorActionPreference='Stop';"
                "[Console]::OutputEncoding=[Text.Encoding]::UTF8;"
                f"{cmd}; exit $LASTEXITCODE")
    return cmd

def kill_tree(pid: int):
    if IS_WIN:
        subprocess.run(["taskkill", "/PID", str(pid), "/T", "/F"],
                       capture_output=True, creationflags=0x08000000)
    else:
        import signal
        try: os.killpg(os.getpgid(pid), signal.SIGKILL)
        except Exception: pass

# ----------------------------------------------------------------- the tools
READ_FILES: set[str] = set()     # enforce read-before-edit

def t_read_file(path, offset=1, limit=2000):
    p = safe_path(path)
    if os.path.isdir(p):
        raise IsADirectoryError(f"{p} is a directory; use list_dir")
    text, _, _ = read_text(p)
    lines = text.split("\n")
    start = max(1, int(offset))
    chunk = lines[start - 1 : start - 1 + int(limit)]
    READ_FILES.add(os.path.normcase(p))
    body = "\n".join(f"{start + i:6d}\t{l}" for i, l in enumerate(chunk))
    return (f'<file path="{p}" lines="{start}-{start + len(chunk) - 1} '
            f'of {len(lines)}">\n{body}\n</file>')

def t_write_file(path, content):
    p = safe_path(path)
    existed = os.path.exists(p)
    eol, bom, old = "\n", False, ""
    if existed:
        old, eol, bom = read_text(p)
    confirm(f"{'Overwrite' if existed else 'Create'} {p}", diff(old, content))
    n = write_text(p, content, eol, bom)
    READ_FILES.add(os.path.normcase(p))
    verb = "Overwrote" if existed else "Created"
    return f"{verb} {p} ({n} bytes, {len(content.splitlines())} lines)."

def t_edit_file(path, old_string, new_string, replace_all=False):
    p = safe_path(path)
    if os.path.normcase(p) not in READ_FILES:
        raise PermissionError(f"read_file {p} before editing it")
    if old_string == new_string:
        raise ValueError("old_string and new_string are identical")
    text, eol, bom = read_text(p)
    needle = old_string.replace("\r\n", "\n")       # CRLF-proof matching
    count = text.count(needle)
    if count == 0:
        raise ValueError(
            f"old_string not found in {p}. Check indentation; line endings are "
            f"normalized to LF for matching, so that is not the cause. "
            f"Re-read the file and copy the text exactly.")
    if count > 1 and not replace_all:
        raise ValueError(
            f"old_string appears {count} times in {p}; it must be unique. "
            f"Add surrounding context, or pass replace_all: true.")
    new = text.replace(needle, new_string.replace("\r\n", "\n"),
                       -1 if replace_all else 1)
    confirm(f"Edit {p}", diff(text, new))
    write_text(p, new, eol, bom)
    return f"Edited {p}. {count if replace_all else 1} replacement(s)."

def t_delete_file(path, recursive=False):
    p = safe_path(path)
    if os.path.normcase(p) == os.path.normcase(ROOT):
        raise PermissionError("refusing to delete the project root")
    confirm(f"DELETE {p}" + (" (recursive)" if recursive else ""), "")
    for attempt in range(5):                        # AV / handle-lock retry
        try:
            if os.path.isdir(p):
                shutil.rmtree(p) if recursive else os.rmdir(p)
            else:
                size = os.path.getsize(p)
                os.remove(p)
                return f"Deleted {p} ({size} bytes)."
            return f"Deleted directory {p}."
        except PermissionError as e:
            if attempt == 4:
                raise PermissionError(
                    f"{e}. On Windows this usually means the file is open in "
                    f"another program or a process is running from that "
                    f"directory. Close it and retry.") from e
            time.sleep(0.05 * (2 ** attempt))

def t_run_command(command, description, cwd=None, timeout_ms=120_000):
    workdir = safe_path(cwd) if cwd else ROOT
    confirm(f"{description}\n  $ {command}", "")
    env = {**os.environ, "PYTHONIOENCODING": "utf-8", "PYTHONUTF8": "1",
           "NO_COLOR": "1", "TERM": "dumb", "CI": "1",
           "MSYS_NO_PATHCONV": "1"}
    flags = 0x08000000 if IS_WIN else 0          # CREATE_NO_WINDOW
    proc = subprocess.Popen(
        [SHELL_EXE, *SHELL_ARGS, wrap_command(command)],
        cwd=workdir, env=env, stdin=subprocess.DEVNULL,
        stdout=subprocess.PIPE, stderr=subprocess.PIPE,
        creationflags=flags,
        start_new_session=not IS_WIN)
    try:
        out, err = proc.communicate(timeout=min(int(timeout_ms), 600_000) / 1000)
        code = proc.returncode
        timed_out = False
    except subprocess.TimeoutExpired:
        kill_tree(proc.pid)
        try:
            out, err = proc.communicate(timeout=2)
        except subprocess.TimeoutExpired:
            out, err = b"", b""
        code, timed_out = -1, True
    body = (f"<exit_code>{code}{' (0x%08X)' % (code & 0xFFFFFFFF) if code and code > 255 else ''}</exit_code>\n"
            f"<stdout>\n{truncate(clean_output(out))}</stdout>\n"
            f"<stderr>\n{truncate(clean_output(err))}</stderr>")
    if code == 9009:
        body += "\n<hint>exit 9009 = command not found on PATH</hint>"
    if timed_out:
        raise TimeoutError(f"Command timed out after {timeout_ms} ms; the "
                           f"process tree was killed.\n{body}")
    return body

def main(prompt: str):
    client = anthropic.Anthropic()
    messages = [{"role": "user", "content": prompt}]
    for _ in range(MAX_ITERS):
        resp = client.messages.create(model=MODEL, max_tokens=16000,
                                      system=SYSTEM, tools=TOOLS,
                                      messages=messages)
        if resp.stop_reason == "refusal":
            print("refused:", resp.stop_details); return
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason == "max_tokens":
            print("output truncated; a tool call may be incomplete"); return
        if resp.stop_reason != "tool_use":
            for b in resp.content:
                if b.type == "text": print(b.text)
            return

        results = []
        for b in resp.content:
            if b.type == "text" and b.text.strip():
                print(b.text)
            if b.type != "tool_use":
                continue
            print(f"[tool] {b.name} {json.dumps(b.input)[:160]}")
            try:
                fn = DISPATCH.get(b.name)
                if fn is None:
                    raise KeyError(f"Unknown tool {b.name!r}. Available: "
                                   f"{', '.join(DISPATCH)}")
                results.append({"type": "tool_result", "tool_use_id": b.id,
                                "content": truncate(str(fn(**b.input)))})
            except Exception as e:
                results.append({"type": "tool_result", "tool_use_id": b.id,
                                "content": f"{type(e).__name__}: {e}",
                                "is_error": True})
        messages.append({"role": "user", "content": results})
    print("iteration cap reached")

Notes on what this 250 lines gets right, which most first attempts get wrong:
  * `safe_path` runs before every filesystem touch, including run_command's cwd.
  * stdin=DEVNULL, so an interactive prompt fails in milliseconds instead of
    hanging for the full timeout.
  * NO_COLOR/TERM=dumb/CI=1 in the child env suppresses most ANSI and spinners
    at the source, which is cheaper than stripping them afterwards.
  * The timeout kills the TREE and then re-drains the pipes with its own
    deadline.
  * Line endings and BOM round-trip, and edit matching happens in LF space.
  * Every failure becomes a tool_result with is_error -- the loop never dies.
  * A user denial is returned to the model as text, not raised, so the model can
    propose an alternative.

Verified behaviour (the helpers above were exercised directly):
  * write -> read -> edit -> delete round-trips, with correct byte and line counts
    for content with and without a trailing newline.
  * A file written as UTF-8-with-BOM and CRLF stays BOM + CRLF after an edit whose
    old_string used LF: b'\xef\xbb\xbfline one\r\nline two\r\n' edited with
    old_string "line one\nline two" yields
    b'\xef\xbb\xbfline one\r\nline TWO\r\n'. This is the PART 11.5 fix working.
  * safe_path rejects "../../etc/passwd".
  * NOTE: the reserved-device-name check and the drive-relative check are gated on
    IS_WIN, so they are no-ops when you run this on Linux/macOS -- "nul.txt" is a
    legitimate filename there. Test those two branches ON WINDOWS, or temporarily
    force IS_WIN = True to unit-test them.

// run.ts -- the Windows-correct parts of a run_command tool in Node.
import { spawn } from "node:child_process";
import { existsSync } from "node:fs";

type Result = { exitCode: number; stdout: string; stderr: string; timedOut: boolean };

const PWSH = [
  "C:\\Program Files\\PowerShell\\7\\pwsh.exe",
  "C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe",
].find(existsSync);

export function runCommand(command: string, cwd: string, timeoutMs = 120_000):
    Promise<Result> {
  const isWin = process.platform === "win32";
  const [exe, args] = isWin && PWSH
    ? [PWSH, ["-NoProfile", "-NonInteractive", "-NoLogo", "-Command",
        `$ErrorActionPreference='Stop';` +
        `[Console]::OutputEncoding=[Text.Encoding]::UTF8;` +
        `${command}; exit $LASTEXITCODE`]]
    : isWin
      ? [process.env.COMSPEC ?? "cmd.exe", ["/d", "/s", "/c", command]]
      : ["/bin/bash", ["-lc", command]];

  return new Promise((resolve) => {
    const child = spawn(exe!, args, {
      cwd,
      // shell:false -- we are spawning the shell ourselves, deliberately.
      // Never pass shell:true with interpolated data (see PART 11.6).
      shell: false,
      windowsHide: true,                       // no flashing console windows
      stdio: ["ignore", "pipe", "pipe"],       // stdin closed on purpose
      detached: !isWin,                        // POSIX process group
      env: { ...process.env, NO_COLOR: "1", TERM: "dumb", CI: "1",
             PYTHONIOENCODING: "utf-8", MSYS_NO_PATHCONV: "1" },
    });

    const out: Buffer[] = [], err: Buffer[] = [];
    let bytes = 0, timedOut = false;
    const CAP = 2_000_000;
    child.stdout.on("data", (b: Buffer) => { if ((bytes += b.length) < CAP) out.push(b); });
    child.stderr.on("data", (b: Buffer) => { if ((bytes += b.length) < CAP) err.push(b); });

    const timer = setTimeout(() => {
      timedOut = true;
      if (isWin) {
        // Kill the TREE. child.kill() leaves grandchildren alive holding the pipes.
        spawn("taskkill", ["/pid", String(child.pid), "/t", "/f"],
              { windowsHide: true, stdio: "ignore" });
      } else {
        try { process.kill(-child.pid!, "SIGKILL"); } catch {}
      }
    }, timeoutMs);

    child.on("close", (code) => {
      clearTimeout(timer);
      const dec = (bs: Buffer[]) =>
        Buffer.concat(bs).toString("utf8")
          .replace(/\x1b\[[0-9;?]*[ -\/]*[@-~]/g, "")
          .replace(/[^\n]*\r(?!\n)/g, "")
          .replace(/\r\n/g, "\n");
      resolve({ exitCode: code ?? -1, stdout: dec(out), stderr: dec(err), timedOut });
    });
    child.on("error", (e) => {
      clearTimeout(timer);
      // WinError 2 here usually means a .cmd shim: npm/tsc/eslint are not .exe.
      resolve({ exitCode: -1, stdout: "", stderr: String(e), timedOut: false });
    });
  });
}

Node-specific Windows notes:
  * `spawn("npm", ["install"])` throws ENOENT -- npm is npm.cmd. Either spawn
    through the shell (as above, where the shell resolves PATHEXT) or resolve the
    shim path first with `which`/`where.exe`.
  * Node >= 18.20/20.12 refuses to spawn .bat/.cmd without `shell: true`
    (CVE-2024-27980). That is a feature: it forces you to decide about escaping.
  * `child.kill()` on Windows is TerminateProcess on that ONE process. Always
    taskkill /T or use a job object.
  * Always set `windowsHide: true`.
  * Decode Buffers explicitly; do not pass `encoding: "utf8"` and hope.

PART 17  PITFALL CHECKLIST
================================================================================
Wire format
 [ ] Append the assistant's FULL content array to history, not just the text.
 [ ] One tool_result per tool_use, same turn, matching id, no orphans.
 [ ] All results for one assistant turn go in ONE user message (Anthropic).
 [ ] json.loads() OpenAI's `function.arguments` -- it is a string.
 [ ] Handle stop_reason max_tokens: the tool call may be truncated; do not run it.
 [ ] Handle stop_reason refusal before reading content.
 [ ] Keep history append-only (preserved thinking); don't rewrite old turns.
 [ ] Accumulate streamed input_json_delta / arguments fragments; parse once.
 [ ] Keep the tools array byte-identical across turns if you use prompt caching.

Tool design
 [ ] Descriptions say when NOT to use the tool and name the alternative.
 [ ] strict:true + additionalProperties:false + required.
 [ ] Error strings are written as instructions for the model.
 [ ] Results include derived signals (diff, diagnostics, exit code).
 [ ] Outputs truncated with an explicit note on how to get more.
 [ ] No tool named "bash" or "str_replace_based_edit_tool" unless it IS the
     Anthropic-defined one with no input_schema.

Execution
 [ ] Validate arguments even with strict:true.
 [ ] Path containment via realpath + relpath, not startswith.
 [ ] Reject reserved device names, ':' in paths, drive-relative paths.
 [ ] Permission gate on write/delete/run; a denial returns is_error, not a crash.
 [ ] Iteration cap and token budget on the loop.
 [ ] Audit log every call.
 [ ] Treat file contents, command output, web pages and MCP results as untrusted
     data, never as instructions.

Windows
 [ ] Tell the model the OS and the shell IN THE SYSTEM PROMPT.
 [ ] cmd.exe gets /d (skip AutoRun) and /s; PowerShell gets -NoProfile
     -NonInteractive.
 [ ] PowerShell command lines end with `; exit $LASTEXITCODE`.
 [ ] File tools never go through a shell.
 [ ] Capture bytes; decode with the console code page or utf-8 + errors=replace.
 [ ] Preserve CRLF and the UTF-8 BOM; match edits in LF space.
 [ ] Kill the process TREE on timeout (taskkill /T /F or a job object).
 [ ] stdin closed, windowsHide/CREATE_NO_WINDOW set.
 [ ] Retry locked-file writes/deletes with backoff; report WinError 32 verbatim.
 [ ] Resolve .cmd/.bat shims (npm, tsc, npx) via PATHEXT; never interpolate
     untrusted data into a batch-file argument.
 [ ] Translate exit 9009 and 0xC0000005-class codes in the result text.
 [ ] Normalize case for any "have I read this file" bookkeeping.
 [ ] Watch MAX_PATH (260) in deep node_modules trees.
